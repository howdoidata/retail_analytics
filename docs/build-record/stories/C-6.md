# C-6: Build the core customer layers

> Build record for one story. Convention: [convention.md](../convention.md). Walkthrough: [build record](../README.md).

## Story spec

**C-6: Build the core customer layers** (CAP-5)

> int_customer_visits (customer × visit number) and dim_customers (signup date, first-touch acquisition channel,
> milestone dates) per the contract, with tests (CAP-5).

Decisions made with Antonio before implementation: no fallback channel, so a customer with no touch at or
before signup keeps a null acquisition channel and fails the build; milestone dates are one map column
(milestone to visit date), so changing the `milestones` variable changes no schema; both models live in
`dbt/models/intermediate/`.

## Change

- PR: batch PR [#5](https://github.com/howdoidata/retail_analytics/pull/5), shared with D-1 and C-2, C-4,
  C-5 follow-ups. C-6 commits: `5414a13` (the models, tests, and record) and `1c36c8c` (the AI review fixes).
- Added `int_customer_visits` (one row per clean visit, numbered per customer by time then order id, with
  calendar days since signup and since the previous visit) and `dim_customers` (signup date and location,
  first-touch acquisition channel, and a `milestone_dates` map built from the `milestones` variable) in
  `dbt/models/intermediate/`, read only from staging; doc blocks for acquisition channel and milestone, and
  a description for every model and column; grain, relationships, and channel tests plus singular tests
  (visit numbers consecutive, days non-negative, milestone dates ascending, visit count equals
  `stg_orders`); staging-shaped fixtures and Python tests (`tests/test_core_layers.py`) for each case in
  the story's input matrix, broken variants, a milestone-variable override, and seed 42. On seed 42 every
  dbt test passes, 43,589 visits match `stg_orders`, and all 18,735 customers have a channel; sign-ups by
  acquisition channel: Paid Social 5,527, Paid Search 3,941, Organic Search 2,812, In-store 1,932,
  Direct/Unknown 1,820, Email 1,509, Referral 1,194 (all simulated).

## Review outcome

- **Human decision:** spec approved by Antonio before implementation (2026-11-03); Antonio merged batch
  PR #5 on 2026-11-03 (merge `9aa5ce0`).
- **AI review findings:** three AI review passes (blind diff review, edge cases, verification gaps) before
  human review; the verification-gap pass found no gaps. Accepted findings were fixed in a follow-up C-6
  commit on the batch branch.

| Source | Finding | Decision | Reason |
|---|---|---|---|
| AI review | First touch was ordered to the minute, so a later touch in the same minute with a lower id beat the earliest one, and the doc said "signup minute" where the filter uses the exact time | Accepted | Ordered by exact touch time, then touch id; doc block and fixture corrected |
| AI review | No broken fixture showed the visit-count test can fail | Accepted | Added an order of an unknown customer, which fails it |
| AI review | The `milestones` variable is not validated (zero, negatives, an empty list) | Rejected | The default is set in the project; a guard adds complexity for overrides nobody makes |
| AI review | Extra dbt tests (milestone dates equal the nth visit, one-to-one links to staging, `signup_location` values) | Rejected | Pinned by exact fixture rows, true by construction, or already tested in staging |
| AI review | Fixture column types could drift from the real staging types | Rejected | The seed-42 test builds the real staging models every run |
| AI review | Other claims (touch join on non-unique emails, staging tests now failing on intermediate rules) | Rejected | Staging tests emails as unique; the raw fixtures pass the intermediate tests |
